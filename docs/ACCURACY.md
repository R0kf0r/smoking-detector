# ACCURACY: как добиваемся высокой точности

Приоритеты команды: **1) корректность** (Event F1 по протоколу SPEC §6), 2) устойчивость к условиям (сезоны, ночь), 3) потенциал удешевления, 4) внешний вид (см. `docs/DESIGN.md`). Если пункты конфликтуют, побеждает тот, что выше.

## 0. Принцип

Точность мы не обещаем, а меряем. Любое изменение, которое может на неё повлиять, сопровождается цифрами оценщика «до» и «после» на одном и том же наборе. Скрытый набор для этого не используется.

Цена ошибки (оценка): в скрытом наборе около 12 положительных эпизодов. Один пропуск стоит ≈8 п.п. recall, поэтому каждый сценарий из списка организаторов нужно продумать заранее.

Обработка может идти долго, это не страшно: правила разрешают сдать заранее рассчитанный файл, если тот же конвейер запускается на одном выданном примере. Значит, для итогового прогона можно брать тяжёлые и точные настройки.

## 1. Где будут ошибки: сценарии организаторов

## 2. Архитектура: сначала не пропустить, потом не ошибиться

**Этап A — кандидаты.** Цель — высокая полнота.

- Люди: YOLO26-pose крупного размера (`l` или `x`) с входом 1280 px и выше. Частота — 15 к/с или все кадры, если хватает времени.
- Трекинг: BoT-SORT с ReID (`with_reid: True`, `model: auto`) и увеличенным `track_buffer`. После прогона — офлайн-склейка треклетов, близких во времени и пространстве.
  - **`appearance_thresh: 0.8` или выше, НЕ 0.25.** В Ultralytics это минимальная похожесть по внешности: в коде расстояние сравнивается с `1 − appearance_thresh`. Значение 0.25 взято из оригинального BoT-SORT, где это порог расстояния; в Ultralytics оно разрешило бы склеивать непохожих людей.
  - `proximity_thresh: 0.5` (по умолчанию).
  - `track_buffer` считается в обработанных кадрах (`max_frames_lost = track_buffer`). Ставить так, чтобы выходило 3–5 с: при 25 к/с это 75–125, при обработке каждого второго кадра — вдвое меньше.
  - Склейка событий: если цикл на новом ID начался в пределах ~2 с после конца цикла на старом ID и рамки перекрываются (IoU > 0,5), считать их одним человеком.
- Поза, вариант 1: 17 точек COCO из YOLO26-pose.
- Поза, вариант 2: top-down по увеличенным кропам людей — RTMPose или RTMW (133 точки, есть лицо и пальцы) через rtmlib. Какой вариант лучше, решает F1 на эталоне.
- Сигнал «кисть у рта»: минимум по двум рукам от расстояния (точка кисти, точка рта), делённого на масштаб человека (длина торса или размер головы).
  - Стартовые значения для 17 точек (подбираются на эталоне): кисть = запястье + 0,2…0,3·(запястье − локоть); рот = нос + 0,6·(нос − середина глаз); масштаб = длина торса (центр плеч — центр бёдер), если бёдра не видны — 0,3·диагональ рамки; порог «у рта» d ≈ 0,15–0,2.
- Сглаживание сигнала, учёт уверенности точек, интерполяция коротких провалов. Обработка офлайн, поэтому сглаживание без задержки: центрированная медиана или фильтр Савицкого–Голея. Фильтр One Euro (mincutoff 1.0, beta 0.007) нужен только для режима реального времени.
- Пауза у рта — строго по правилам 0,5–5 с (допуск на шум ±0,2 с). Поднимать нижнюю границу до 1,5 с нельзя: эталон размечен по правилам организаторов, короткие затяжки станут пропусками.
- Время кадра — по меткам времени видео (PTS через PyAV или `CAP_PROP_POS_MSEC` в OpenCV), а не номер кадра / fps: у камер бывает переменная частота кадров.
- Если на эталоне теряются кисти: добавить RTMPose-m 256×192 через rtmlib на кропах **уже отслеженных** людей (запас 1,25 от рамки). YOLO26 оставить для людей и ID — заменять его целиком нельзя, сломается трекинг.
- Детектор циклов с мягкими порогами и гистерезисом: подход → пауза → отход.
- **Кэш:** результаты тяжёлого этапа (рамки, ID, точки по кадрам) сохраняем в файл. Тогда правила и пороги перебираются за секунды, без повторного прогона моделей.

**Этап B — проверка кандидатов.** Цель — высокая точность.

- VLM локально, самая крупная модель, которая помещается в память (см. research.md). По умолчанию — `mlx-vlm` с `mlx-community/Qwen3-VL-4B-Instruct-4bit` (Apache-2.0, около 3 ГБ); если Ollama уже настроена, можно оставить её. Берём 3–5 кадров в момент паузы у рта, кроп с головой и кистью, увеличенный не меньше чем до 336 px. Закрытый список ответов в JSON: сигарета, вейп, телефон, бутылка/стакан, еда/ручка, только рука, не видно; temperature 0. Решение — по большинству кадров; ответ «не видно» решение не меняет.
- Детектор предметов COCO (`cell phone`, `bottle`, `cup`, `wine glass`) на увеличенном кропе — вето.
- Кинематика: длительность паузы, обе руки у лица, запрокидывание головы.

**Этап C — события строго по SPEC §3–4.** Два цикла за 20 с либо один цикл плюс прямой признак (VLM уверенно видит сигарету или вейп). Объединение при паузе ≤ 15 с, только внутри одного человека. Уверенность складывается из числа циклов, согласия VLM и качества трека.

## 3. Подбор порогов без самообмана

**Эталон** — сценарные ролики организаторов, выданные 8 октября. Они лежат в `private/reference/positive/` и `private/reference/negative/`. Это реальные камеры, поэтому для точности они важнее любых видео из интернета.

**Разметка.** Если организаторы не дали разметку, её делает человек: Claude эти видео не видит. Файл — `labels/reference.csv` (в нём только время и метки, без кадров, поэтому Claude может его читать):

| Колонка | Смысл |
|---|---|
| `clip_id` | имя файла без расширения |
| `camera_id` | камера, если известна |
| `label` | POSITIVE, NEGATIVE или IGNORE |
| `start_sec`, `end_sec` | границы события по SPEC §4 (для негатива — границы действия) |
| `scenario` | P01–P08 или N01–N08, если понятно |
| `person_hint` | где человек в кадре: «слева», «в центре» (без примет внешности) |
| `person_track_id` | ID трека; заполняется после первого прогона по видео с отметками |
| `comment` | сомнения, причина IGNORE |

- Время удобно смотреть в QuickTime Player. Для позитива событие идёт от начала движения руки в первом цикле до отвода руки после последнего. Всё спорное помечается IGNORE с причиной.
- После первого прогона открой свои видео с отметками из `private/renders/` (локально, не в чате), найди ID нужного человека и впиши его в `person_track_id`. Тогда оценщик проверяет и IoU рамок, как в протоколе.

**Бюджет времени.** Скрытый набор снимут 9-го днём, а материалы нужно сдать до 23:59 того же дня. Поэтому уже сегодня на эталоне замеряем, сколько секунд уходит на минуту видео в точном и в экономном режимах, и выбираем режим, который успевает с запасом.

**Как подбирать:**

- Данных мало: 1–4 положительных клипа. Поэтому параметров мало, и все они физически осмысленные: пауза 0,5–5 с взята из правил, порог расстояния задан в долях размера головы.
- Leave-one-clip-out: подбираем пороги на всех клипах, кроме одного, проверяем на нём и повторяем для каждого клипа.
- Рабочую точку выбираем по максимуму F1, но следим и за FP в час на фоновых фрагментах.
- HMDB51 и Pexels нужны только для санитарной проверки. Под них пороги не подгоняем.

## 4. Корректность кода — тоже точность

- Оценщик и автомат циклов покрыты тестами на ручных примерах; эти примеры человек проверяет на бумаге.
- Независимое ревью: в новой сессии Claude Code сверяет `evaluate.py` и правила событий со SPEC и ищет расхождения.
- Каждый выходной файл проходит валидатор организаторов.
- Визуальный аудит на публичных видео: оверлей и график «след жеста» (`docs/DESIGN.md`).

## 5. Порядок внедрения: больше всего F1 на час работы (оценка)

1. Оценщик и тесты — без них улучшать нечего.
2. Базовый конвейер: YOLO26-pose, трекинг, правила, кэш.
3. Проверка кандидатов через VLM и вето COCO: снижает FP на N01–N03, N06, N07.
4. ReID и склейка треков: P05, P08.
5. Модель крупнее или top-down поза: дальние зоны, профиль P02.
6. Подбор порогов на эталоне, затем фиксация.

## 6. Сезоны и условия съёмки (масштабируемость)

| Условие | Что ломается | Что помогает |
|---|---|---|
| Зима | объёмная одежда, капюшоны, шарф на лице (часто IGNORE), перчатки; снег даёт пересвет и низкий контраст; пар изо рта на морозе | сигнал по геометрии позы меньше зависит от одежды и фона, чем классификаторы по виду; пар не используем как признак |
| Короткий день, ночь, ИК | монохромный кадр, шум, смаз | проверка на сером «ИК»-кадре с шумом; для обучаемых частей — такие же аугментации |
| Лето | резкие тени, листва, солнечные очки, больше людей и перекрытий | ReID и склейка; маска зоны |
| Дождь, туман | капли на объективе, размытие, зонты закрывают руки | порог видимости, IGNORE вместо догадок |

- Стресс-тест: одни и те же клипы прогоняем с искусственными ухудшениями (серый кадр, шум, размытие, сжатие, низкий контраст) и пишем в отчёт, насколько падает метрика.
- Калибровка под камеру: зона, масштаб человека с учётом перспективы, свой порог видимости.
- Честно: устойчивость к сезонам подтверждается только реальными записями этих сезонов. В отчёте это пункт «улучшения»: попросить у «Видеофор» архив зимних и ночных записей для проверки.

## 7. Потенциал удешевления

- **Каскад.** Дешёвый этап работает на всех кадрах (лёгкая модель, 5–10 к/с, только люди в зоне), дорогой — только на кандидатах. Стоимость растёт с числом кандидатов, а не с часами видео.
- **Метрика стоимости в отчёте:** секунды обработки на час видео одной камеры и доля кадров, дошедших до дорогого этапа.
- **Дистилляция.** Тяжёлый конвейер (крупная поза и VLM) размечает архив, на этой разметке обучается маленькая модель по последовательностям точек скелета, которая работает на CPU или edge-устройстве.
- **Квантизация и экспорт** (ONNX, CoreML, TensorRT INT8), пропуск кадров без людей.
- **Лицензии — тоже стоимость.** Ultralytics распространяется под AGPL-3.0, для закрытого продукта нужна платная лицензия. Альтернативы под Apache-2.0: rtmlib (RTMPose, RTMDet, YOLOX).

## 8. Чего не делать ради «точности»

- Не дообучать большие модели на четырёх клипах.
- Не подгонять пороги под отдельный клип.
- Не использовать дым и пар как признак.
- Не подключать облачные модели к видео объекта.
- Не менять ничего после тега `freeze-*`.
